# Прототип аудита конфигураций гибридного облака

Автор: Пузей Владимир Александрович. Учебный прототип версии 1.0.1 к магистерской диссертации «Автоматизация аудита безопасности гибридного облака на примере X5 Retail Group».

Программа импортирует две модельные JSON-выгрузки, приводит их к общей схеме, выполняет 12 контролей и сохраняет HTML, JSON и CSV. Результаты разделяются на PASS, FAIL, UNKNOWN, ERROR и NOT_APPLICABLE. Свидетельства содержат использованные поля и SHA-256; действующее исключение не меняет FAIL на PASS.

Данные синтетические. Программа не подключается к инфраструктуре X5 и не оценивает ее фактическую защищенность. Проект корпоративного сервиса шире этого прототипа: адаптеры реальных API, SSO, ITSM, управление секретами и PostgreSQL описаны в диссертации, но здесь не реализованы.

## Запуск

Требуется Python 3.10 или новее. Внешних Python-зависимостей нет. Проверено на Python 3.12.14, Darwin arm64.

Из каталога проекта выполните:

```sh
python3 audit_core.py private.json public.json --exceptions exceptions.json --now 2026-10-14T12:00:00+00:00 --output demo/before --database demo/audit.db
```

Откройте `demo/before/audit.html` в браузере. Ожидаемая сводка: 480 пар; 98 применимых оценок; 69 PASS, 13 FAIL, 15 UNKNOWN, 1 ERROR, 382 NOT_APPLICABLE; одно действующее исключение. Нулевой код завершения означает успешное формирование отчета; нарушения отражены внутри отчета.

## Повторный аудит

Файл `public-fixed.json` отличается от `public.json` только сетью административного доступа у CASE-02: `0.0.0.0/0` заменено на `10.10.0.0/24`.

```sh
python3 audit_core.py private.json public-fixed.json --exceptions exceptions.json --now 2026-10-14T12:00:00+00:00 --output demo/after --database demo/audit.db
```

Ожидается переход NET-01 для public:CASE-02 из FAIL в PASS, 70 PASS и 12 FAIL; остальные счетчики прежние, EX-39 сохранено. База содержит два запуска, 80 записей ресурсов и 960 оценок. Это изменение учебного входа; программа не исправляет конфигурации облака.

Повторное сохранение идентичного запуска в ту же SQLite-базу отклоняется. Для повторения всей демонстрации используйте новый выходной каталог и новую базу, например `demo2/before` и `demo2/audit.db`. Контрольное время фиксировано для воспроизводимости возрастов ключей и свидетельств.

## Проверки

```sh
python3 control_examples.py
python3 boundary_checks.py
```

Ожидается 40 основных, 8 интеграционных и 20 граничных успешных проверок. Первая команда заново формирует исходные JSON-файлы, отчеты и `protocol.json` в каталоге проекта; вторая создает `boundary_protocol.json`. Выполняйте их в отдельной копии, если сохраняете результаты ручной демонстрации. Проверки охватывают заданные примеры и не доказывают отсутствие всех дефектов.

Измерения времени относятся только к оценке данных в памяти. Чтение файлов, HTML, запись SQLite и сетевой сбор в них не входят; повторный запуск дает другое фактическое время.

## Состав

| Файл | Назначение |
|---|---|
| audit_core.py | CLI, нормализация, контролы, свидетельства, SQLite и отчеты |
| control_examples.py | Размеченные сценарии, интеграционные проверки и измерение |
| boundary_checks.py | Точные границы, неправильные типы и повторная оценка |
| private.json / public.json | Модельные входы двух форматов |
| public-fixed.json | Один исправленный вход для повторной проверки |
| exceptions.json | Учебные согласованные исключения |

Реализованная SQLite-схема содержит `runs`, `resources`, `assessments`. Полная проектная ER-модель системы в диссертации включает дополнительные каталоги, источники, владельцев, согласования и задачи. Права на распространение исходного кода определяются автором; лицензия открытого ПО этим комплектом не назначается автоматически.
